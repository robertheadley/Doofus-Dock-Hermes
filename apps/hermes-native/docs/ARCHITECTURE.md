# Hermes Native architecture and ownership

## Current completion boundary

The active user goal is a first usable native Hermes agent-workflow UI against pinned snapshot `8783054ef6cbafd86f10892241436862c1171a66`, covering chat, tools, skills, plugins/MCP and required connection/context/attachment support. This goal is still in progress; its completion is not established. Pixel parity and unrelated Desktop administration are deferred. The 499-row matrix is the broad source inventory; scoped capability evidence and live runtime verification remain incomplete. Hermes owns agent/tool execution; the native app owns chat UI and request/state presentation; DoofusDock provides the UI framework. `background.complete` is routed into the originating active or uniquely cached transcript as a bounded system row; known task IDs de-duplicate replay, and session/profile ownership prevents cross-profile updates. This behavior has headless evidence only. Doofus Hermes backporting follows completion of the new UI.

Saved remote Gateway startup loads only a credential matching the selected remote endpoint. If neither a token nor OAuth session is available, startup fails closed and shows the credential requirement; it must never attach to the local Gateway while retaining the remote connection identity. A saved-connection picker and complete per-connection lifecycle/result fencing remain open.

Prompt history metadata is read asynchronously through the owning Gateway connection. The index request carries a stable request ID, stored session ID, profile, connection ID and cursor; responses are accepted only when that tuple still matches the pending request. It contains prompt previews and durable row IDs only, never tool or assistant bodies. The index is cached by profile/connection/session with a 12-session cap and exposes an explicit refresh action. Successful prompt admission invalidates matching loaded indexes; an automatic first-page refresh preserves old rows while pending and replaces them on success. This detects mutations submitted through this client, while time-based expiry and changes from another client remain open. Selecting an unloaded row requests the pinned `/messages/around` route with a 120-row cap; response validation requires the requested session/profile, anchor row, count, ordering and consistent bounds. The resulting transcript window replaces only that owner cache, and only updates the visible chat when its connection/profile/session is still active. The transcript selects the last prompt at or above viewport top plus eight points, falls back to its first prompt when none is above the viewport, and selects the last prompt while following bottom; matching transcript and indexed entries expose a Current marker. Headless behavior is covered; authenticated live Gateway, packaged Windows and physical scroll input remain open.

The chat toolbar now shows session-cumulative token totals and the latest reported context occupancy. `session.usage` events are accepted only from the current Gateway connection and only applied to a uniquely matched connection/profile/runtime/stored-session view; nested desktop usage projections and top-level canonical counters are both supported, and sparse updates retain figures they omit. The UI labels estimated context separately. Headless regressions cover event parsing, partial merges, stale connection/session rejection, profile isolation, and accessible toolbar rendering. Live Gateway, physical Windows, and source-paired acceptance remain open.

## Older prompt history windows

When a displayed transcript window came from `/messages/around`, its older-page action uses the profile/connection/session-owned prompt metadata index to locate the nearest durable user prompt before the first visible prompt. If the index has not reached the window anchor, it requests further index pages and continues the lookup on their owner-matched responses. It then fetches the predecessor with the bounded around-row Gateway route. The response is merged only when `older_offset + older_message_count >= current_offset`; otherwise the native chat displays the older page alone to avoid implying that messages across the gap are adjacent. Existing request/session/profile/connection correlation fences late responses. The REST transport cannot cancel a backend read, and the UI does not yet expose cancel-and-replace semantics or proven physical scroll anchoring. This Hermes-owned transcript behavior leaves DoofusDock's canonical layout document unchanged.

Prior-message editing is owner-scoped to a unique persisted user row and submits `prompt.submit` with explicit truncation confirmation. Local history updates only after an admission receipt. For a definitive Gateway error code 4009, the UI preserves that code, interrupts the matching session, waits for the matching owner receipt, then retries the same edit once; a second refusal restores the edit draft. If submit is explicitly refused because its runtime ID is stale, the Gateway resumes the exact stored session and emits a connection-scoped runtime-rebind event before retrying the unchanged edit once. The app updates the matching stored-session/profile/connection view and pending submission before it processes the retry receipt or subsequent stream events. A mismatched stored owner fails closed without retry; unknown prompt-submit or interrupt outcomes never replay a destructive edit. Pinned source replaces the historical user turn with text, dropping old attachment parts. The native edit dialog can stage new file/image uploads on the same profile/session/connection owner, then includes Gateway-returned refs in the replacement prompt; the active composer attachments remain separately owned. Local WebSocket and app ownership fixtures pass; live Gateway behavior and native Windows picker/drop interaction remain unverified.

## Ownership

- **Hermes Python gateway:** authoritative session execution, backend requests, approvals, recovery and backend events. Rust must not recreate agent logic.
- **Hermes Native app core:** owns navigation and view-specific state; feature mutations use the same approved Hermes gateway methods as source UI.
- **egui/eframe host:** owns rendered widgets, accessibility integration and native windows. Hermes Native remains a standalone app when development control is disabled.
- **DoofusDock:** owns canonical `LayoutDocument`, revision-checked layout changes, profiles and presentation. App owns panel content. Logical layout acceptance and physical OS behavior are separate evidence.
- **Semantic control service (in progress):** the initial typed app-action registry is shared by human route/layout controls and the agent protocol; remaining actions, permissions, and feature-level DoofusDock/Hermes operations are still open.
- **Development Debug Bridge (planned):** authenticated local transport for bounded state, semantic actions, events and diagnostics. It is distinct from Hermes gateway and disabled/absent in production.
- **Development supervisor (planned):** declarative reload, Rust rebuild/restart, generation/readiness handshake and automation-client recovery.

Moving panes beyond the active session, cross-window session synchronization, physical Windows lifecycle and source-paired acceptance remain open. `src/gateway.rs` owns the Hermes transport. It restores existing sessions, creates a fresh session, submits its initial prompt using the runtime session ID, and forwards basic message lifecycle/delta events. Full-history search uses a separate bounded worker with a profile-scoped native HTTP ticket, keeping it off the WebSocket event actor; requests are loopback-only and disable ambient proxies and redirects. `src/app.rs` owns UI and route state, including stored-session navigation, 200 ms session-search debounce/request fencing, ranked full-history result mapping with loaded local matches, compact `last_active` display and the active runtime ID used to fence incoming events. The active composer exposes Stop through `session.interrupt` using the active runtime ID and execution generation. On `session not found`, the Gateway resumes the exact owner-matched stored session without replay, validates its identity and fresh generation, and retries interrupt once; the app rebinds only the matching profile/connection/session view. Resume failure preserves the original interrupt error. Correlated success preserves partial assistant text and marks it terminal, while an already-idle receipt unblocks the composer. `approval.request` events render accessible cards with only backend-offered once/session/always/deny decisions; `approval.respond` carries the active runtime session and execution generation. Single-question `clarify.request` events render source choices, free text, multi-select answers and skip; `clarify.respond` carries the prompt's active runtime session and generation. Batch server-request `clarify` cards stage all question answers, restore replay answers as editable controls, and send sequential `clarify.lock` RPCs in source order; Skip returns an empty server-request result. Both prompt flows validate correlated receipts and disable controls while offline or pending; local fixtures cover scope, mismatched receipts, stale actions and accessible offline state. Live gateway behavior is unverified. Remaining chat gaps include full source create options/retry, other server-request methods and in-flight request multiplexing, complete event reconciliation, idempotent submit recovery and reconnect. The opt-in `agent-automation` feature builds `hermes-automation`, a headless egui_kittest harness around the same `HermesNativeApp::draw` path. It disables gateway startup, uses an isolated temporary layout profile for success and fallback paths, and removes that profile on exit. This proves semantic widget input and headless frame capture for current UI code, but bypasses the OS windowing host. The default build excludes the runner and its renderer dependency.

## Saved Gateway session owner boundary

Workspace preferences persist secret-free local/remote Gateway descriptors and a selected descriptor ID. Session rows may carry `connection_id`; before the native sidebar opens or mutates such a row, the app resolves it through `SessionOwnerRegistry` and requires the resolved owner to equal the selected descriptor. Untagged legacy rows route through that selected descriptor. Unknown and non-selected tagged owners are refused before dispatch. This is a fail-closed boundary for the current single-`GatewayDiscovery` app, not multi-connection support. `GatewayDiscovery::shutdown` drops its status/event receivers before closing command senders, so queued late events cannot be consumed by the retired UI; its socket actor notices channel closure after the 100 ms read timeout. It does not join/cancel already-running HTTP work or an attach blocked in network setup, and it does not replace the required connection owner on cached state or request/result messages.

Read-only diagnostics have narrower scope than mutating actions. Every mutation validates schema, actor, permission, expected state/layout revision and idempotency key. Asynchronous acceptance is not success; report terminal outcomes. The bridge must not be an arbitrary shell/filesystem proxy or bypass Hermes approval.

## Security and lifecycle

Development control is loopback-only with an unpredictable token or equivalently protected local transport. Authenticate writes, bound schemas/payloads, redact sensitive values, audit decisions, support revocation and keep the feature out of production packages. A supervisor should retain the last working build where possible, report failed builds, prevent stale clients from targeting an old process generation, reconnect to the existing Hermes gateway, and never duplicate active submissions. State survival must be explicit by category; do not claim process-local state survives restart without evidence.

## Evidence layers

1. **Core/protocol contracts:** schemas, permissions, persistence, gateway correlation/idempotency and error paths.
2. **Semantic UI integration:** app UI/control service, accessible queries, user-equivalent actions, receipts and headless screenshots.
3. **Physical Windows host:** actual executable, focus, keyboard/IME, native window moves, docking, DPI, multi-monitor and screenshot parity.

Headless screenshots or accepted commands are not physical-host evidence. Visual and functional parity are tracked separately; both are required.

## Files panel

`files::FileBrowserState` owns transient presentation state: selected root, expanded paths, loaded directory entries, errors, selected row, and the active ignored-file filter. The root is derived from the active route's matching profile-scoped `SessionSummary.cwd`. A dedicated worker performs local `read_dir` and `.gitignore` matching off the UI thread, and responses carry root plus generation identity so a project switch, filter change, or refresh cannot apply stale results. The per-project “Show gitignored files” choice is persisted in `ui-preferences.json`; it bypasses gitignore reads while preserving source-defined transport exclusions. Default filtering uses the nearest `.git` marker, adds ancestor and nested `.gitignore` files through the listed path, and preserves ignored nested repository roots. Activating a file row opens a dynamic DoofusDock file-preview pane; later previews join its tab group. `FilePreviewStore` reads and decodes content on a worker, rejects binary/oversized text by default, offers an explicit Preview anyway path, and bounds forced text reads to the source's 512 KiB ceiling. Markdown uses the app's cached CommonMark renderer; recognized source files use that renderer's syntax highlighter through a safely chosen code fence. BMP/GIF/JPEG/PNG/WebP images decode to RGBA and SVG vectors rasterize using bounded dimensions before upload to cached egui textures. SVG parsing ignores external image references. PDF pages are individually rasterized by one PDFium 8125 binding confined to the preview worker, then presented as one vertical document with fit-to-pane sizing, 50–300% zoom, page jumps and an eight-page raster cache. HTML files expose Source and Preview modes. On Windows, Preview lazily creates a Wry child WebView2 bound to the eframe main window, follows the active Dock pane bounds, hides when the pane is inactive, and opens the canonical local file URL so relative resources and page JavaScript work; top-level navigation is restricted to the selected document and `about:blank`, while relative subresources still load. A versioned Windows x64 PDFium DLL plus its third-party license bundle is copied next to build output. Preview descriptors use `PersistencePolicy::Never`; `persistent_layout` removes those descriptors and their tree nodes from a cloned document before saving so temporary panes do not leak into restart state. Files and previews remain read-only. Remote filesystem adapters, missing-root fallback, richer context actions, exact Chromium PDF toolbar behavior, exact visual matching and source-paired Windows acceptance remain open requirements.

The opt-in headless agent runner starts at New session for every invocation. ### First-run setup surface

`HermesNativeApp::update_gateway_discovery` marks the first-run setup surface available only after the initial gateway attach returns an error. `show_first_run_setup` renders the source-style blocking choice modal on New session. Connect opens a gateway URL form and normalizes HTTP(S) URLs, including scheme-less hosts, like the pinned Desktop. After 500 ms without an edit, `RemoteProbeWorker` sends a credential-free GET to public `/api/status`; OAuth gateways receive a best-effort `/api/auth/providers` request. The worker has an eight-second timeout, disables redirects, caps each JSON response at 512 KiB, and keeps network work off the UI thread. Request IDs discard results for superseded URLs. The UI displays reachability, detected token/OAuth mode, provider names, native-PKCE support and gateway version. Token mode accepts a masked, zeroizing session-token field; its separate worker checks authenticated `/api/status` and the token-query `/api/ws` handshake. For gateways advertising `native_pkce`, a user-triggered worker opens the gateway authorize URL in the system browser, binds a loopback callback on 127.0.0.1, validates state and redeems the authorization code with its PKCE verifier. OAuth Test rotates sessions within 60 seconds of expiry through `/auth/native/refresh`, then uses the current bearer for authenticated `/api/status`, `/api/auth/ws-ticket` and `/api/ws?ticket=...`. Rotated sessions are encrypted with Windows DPAPI and atomically stored in `native-oauth-tokens.json` under the Hermes Native profile directory; the installed Hermes profile is not touched. Passing tests are fenced by request ID and bound to a private hash of the exact normalized URL/auth/credential payload; edits invalidate the Apply gate. remote HTTP-backed APIs beyond the listed coverage and live attach verification, legacy embedded/password-provider login, and local bootstrap remain incomplete. Install reports that the local bootstrap pipeline is not implemented. The opt-in agent runner's `--first-run-setup-fixture` forces this state in a unique temporary offline profile, and `--type-role ROLE NAME TEXT` disambiguates controls that share an accessible name. Diagnostics expose probe/login/test state but never the URL, verifier, tokens or payload fingerprint.

A 60 ms debounce sends a bare slash to `commands.catalog` and typed queries to `complete.slash`, scoped to the active session or profile. Responses are fenced by request and owner identity, then filtered through the pinned Desktop command registry and interface mode. Accessible suggestion buttons insert the selected command into the draft without submitting it. Arrow navigation, directive chips, mid-message triggers, result caching/invalidation and special local session/skin commands remain unimplemented; live Gateway and source-paired behavior are unverified.

## Transcript find

Native find searches the currently loaded transcript's message body and speaker fields case-insensitively, cycles through matching rows, and scrolls/highlights the matching card. It does not yet walk all text in the rendered chat surface or highlight individual substring ranges as the pinned Desktop renderer does; other panes, live behavior and source-paired acceptance are unverified.


## Older transcript history

Current pagination requests profile-scoped offset pages, fences the response to its session/profile/request tuple, and prepends with boundary deduplication. The pinned Desktop flow reveals a prior prompt using an around-row page and predecessor lookup; a noncontiguous page replaces the current history window. That anchored navigation is not implemented yet.


## Reasoning and answer stream

The transcript reducer scrubs tagged reasoning from `message.delta` before updating the answer bubble and holds incomplete tag prefixes between frames. `reasoning.delta` is associated with the active assistant row, including profile-scoped background transcripts. The Thinking disclosure renders reasoning separately; Simple mode defaults it closed. The accumulated raw stream is temporary and removed when the segment completes, is interrupted by a tool, or fails. Reasoning is exposed only after a Gateway reasoning event indicates the configured stream is enabled. The active profile's `display.show_reasoning` setting is loaded with CLI override precedence and defaults off when unset. A native setting control, live Gateway verification, and source-paired Windows acceptance remain open.

## Tool invocation transcript projection

Gateway `tool.start` and `tool.complete` events are projected into accessible transcript cards keyed by session, tool ID, and execution generation. Reused tool IDs in a later generation remain separate. In Advanced interface mode, each row can expand a collapsed-by-default raw payload disclosure with formatted Arguments and Result; the displayed trace is bounded to 20,000 characters. Simple mode keeps the technical payload hidden. `tool.progress` annotates the matching running row with bounded status text and a percentage; batched MCP rows receive the progress by call-ID suffix. Updates are session/profile scoped and are cleared on tool completion, turn completion, or error. The pinned Desktop additionally groups consecutive invocations into run summaries with live ticking and persisted disclosure; the native UI currently renders individual cards. A separate persisted technical/product tool-view preference is not implemented. Live Gateway behavior, interrupted-turn parity and installed Windows rendering remain unverified.


## Installed skills

The capabilities view consumes Gateway `SkillInfo` rows and filters them case-insensitively by name, category, and description. Skill loading is profile-scoped through the Gateway capability request. This listing slice does not cover skill lifecycle controls or pinned usage ordering; see the generated capability progress view.


Skills search results are filtered by name/category/description, then sorted by usage descending and name ascending. Native tie-breaking uses lowercase ordinal comparison; localized names may order differently from the pinned Desktop locale comparison.


## Skill enable mutations

A skill row dispatches a profile-bound Gateway HTTP mutation. The current skill list is optimistically updated and keyed pending state disables duplicate toggles; response receipts must match request, profile, connection instance and authority epoch. A denial restores the previous `enabled` value and surfaces the error.

The Connectors view also reads the pinned Hermes MCP inventory from `GET /api/mcp/servers` through the bounded HTTP worker. Requests include the selected profile, use a one-use native ticket on verified local loopback, and use configured authentication for remote Gateways. Rows expose transport, command or URL, enabled state, and any known tool count; MCP mutations remain separate work.

MCP server enable/disable uses the pinned `PUT /api/mcp/servers/{name}/enabled` contract and an `{enabled}` payload. Local writes require a verified loopback origin and one-use ticket; remote writes use configured Gateway authentication. The row updates optimistically, then confirms or rolls back on the `{ok}` response. Request, profile, connection instance and authority epoch fence UI state.

## Skill detail reads

The Skills view reads selected skill content from the pinned profile-scoped `/api/skills/content` endpoint. Content requests use the bounded Gateway HTTP worker and validate the response name, source path, and body size before display. UI receipts are accepted only for the same request, profile, Gateway instance, authority epoch, and selected skill; switching owners cannot show the prior profile's content.

The installed Skills view exposes Hermes' batch “Update installed” action through profile-scoped `POST /api/skills/hub/update`. Its receipt must identify the pinned `skills-update` action, after which the UI tails bounded `/api/actions/{name}/status` output and reloads the inventory on a successful exit. Status results are bound to the request, profile, Gateway instance, authority epoch and receipt PID. A failed or uncertain start is surfaced without automatically replaying the mutation; live Gateway, Windows and cancellation/reconciliation behavior remain open.

## Toolsets bulk enable/disable

The Toolsets All switch targets every Desktop-visible toolset, independent of search filtering, and excludes the pinned platform/internal rows. Native requests are sequential to avoid overlapping Gateway configuration read-modify-write operations. Each row is optimistic until its response arrives; denial restores its prior confirmed value and stops the remaining batch. Disconnect clears in-flight state, restores the last confirmed local value and marks the result unknown until refresh. Live Gateway and packaged Windows behavior remain unverified.

Toolsets inventory rows also expose Hermes' configured boolean as “Configured” or “Needs setup”. This matches the pinned detail warning at a summary level. The current API does not include per-toolset missing-key/provider details, so this indicator cannot name the specific prerequisite.

The pinned Desktop's linked-plugin preview-script permissions are app-local Electron state, per plugin and HTTP(S) origin. They are not part of the Hermes Gateway's AgentPluginInfo contract. Hermes Native currently has no Desktop renderer-plugin host or equivalent origin-grant store; PAR-0269 remains explicitly not implemented until such a host exists. The separate Agent Plugins list must not be presented as having these grants.

Installed Agent Plugins with a declared settings schema expose typed manifest-backed controls. Nonsecret changes are sent through `plugins.manage action=settings`; secret fields use the selected profile's authenticated `/api/env` route and never appear in plugin RPC values or readback. This Gateway configuration flow does not implement Electron Desktop renderer-plugin permission grants.


## Transcript Markdown and link safety

Assistant transcript bodies use `egui_commonmark` with the pinned Pulldown parser and native syntax highlighting. Link destinations are registered as CommonMark hooks so the widget cannot directly dispatch arbitrary schemes. Only parsed HTTP(S) URLs with a hostname and no embedded credentials, recognized bare domains normalized to HTTPS, and user-clicked `mailto:` URLs are forwarded through egui's host URL command. Heading fragments remain local; active schemes are blocked. File-like links are reserved from the bare-domain heuristic. A clicked local file opens the existing DoofusDock preview tab only when the active stored/runtime/profile view matches, the Gateway is unauthenticated loopback, the terminal backend is `local`, and canonicalization keeps the existing file inside the reported project directory. Remote paths, container paths, missing files, paths outside the project, and stale/unbound sessions fail closed. The renderer still has partial pinned behavior: remote filesystem previews, audio/video players, tool-owned media routing, the source's broader Markdown preprocessing, and packaged/live/source-paired validation remain open.

The chat composer keeps Gateway-backed slash completions scoped to the active profile/session. Its visible results are keyboard-selectable with ArrowUp/ArrowDown; Enter/Tab and mouse click insert only into the persisted draft and never submit the prompt.


## Failed-turn editing

A user transcript row immediately followed by an assistant error can be edited even without a durable Gateway `row_id`, provided the local user row has a stable submission/message ID. The app fences the edit to the current connection, profile and runtime session and rechecks the ID, original text and adjacency at submit time. This is a normal `prompt.submit`, not a `confirm_truncate` operation. Local history changes only after an admission receipt: the failed user/error pair is removed and the newly admitted prompt is appended while subsequent transcript entries and the live composer remain. Definitive refusal keeps the failed row and restores the edit dialog; uncertain admission does not auto-replay.


## Prior-message edit target resolution

When an eligible displayed user message lacks a numeric durable row ID, the app queues a separate bounded authenticated REST history lookup. The worker verifies the returned session, profile and pagination contract and matches only exact trimmed user text on durable user rows. It uses the existing truncating edit protocol only for a unique match or a duplicate proven to be the newest user row in both the loaded transcript and stored history. Otherwise the dialog submits as a new prompt without truncating history. Request, source text, local message ID, runtime/stored session, profile and Gateway connection fence the result. Adjacent full pages overlap by one exact row; if that boundary changes between offset reads, native refuses to resolve a truncation target and uses the non-truncating submit path. The pinned REST API provides no snapshot cursor, so a change within the final page or after the lookup completes cannot be ruled out by this client-side check; authenticated live Gateway race behavior remains unverified.


## Composer draft persistence

Plain-text composer drafts are stored under the app's user data directory in a dedicated `composer-drafts` directory. Each atomic JSON record is keyed by the existing Gateway connection/profile/session identity, has a 256 KiB text bound, and includes a schema version and write timestamp. The store retains at most 50 records. Invalid, oversized, or mismatched records fail closed and surface a status message; the in-memory draft remains usable. Empty composer state removes the stored record. Attachment data and temporary attachment references are not persisted. In-memory session views containing draft text or attachments are protected from the 32-entry LRU eviction, so this cache may temporarily exceed 32 entries while all candidates contain unsent user state.


## Model changes and composer state

The active session model is changed through an owner-scoped `ChatPolicyMutated` request/receipt. Composer text and attachment chips are app-owned state separate from the model options snapshot; model success updates the session options without rebuilding or clearing the composer. Confirmation-required responses retain the selection as a pending confirmation, and refusal surfaces an error while preserving composer state. Receipt ownership is checked before removing the pending mutation, so a stale profile/session/connection response cannot consume the current operation.

## Tool results and inline diffs

`tool.complete` remains the authoritative completion event. The transcript reducer stores the complete payload fields, while the view presents `result_text`/`summary` independently from `inline_diff` (or the legacy `diff` field). Inline unified diffs are rendered in an expanded-by-default, accessible disclosure with bounded text and line counts; additions, removals, hunk headers and file headers have distinct presentation. Structured `success:true`/`ok:true` takes precedence over stale error metadata; explicit failure fields render as errors; otherwise the row remains `complete` without guessing from free-form text or a stopped turn. Raw arguments, results and diffs are available in Advanced tool payload details. Headless transcript and reducer tests cover these paths; live Gateway and packaged Windows behavior remain unverified.

## Gateway request cancellation

The normal Gateway event channel handles `request.cancel` by exact server request ID. It removes a matching approval or batch-clarification prompt and, when present, requires the event profile to match the prompt profile. Missing IDs, unknown IDs, and owner mismatches are no-ops. Later response acknowledgements for a canceled card do not recreate it. The native client currently does not render the sensitive request methods that the pinned Desktop handler can also cancel.

## Unknown Gateway response outcomes

Approval, clarification, and clarification-lock RPCs distinguish a definite remote JSON-RPC refusal from an ambiguous transport result. A timeout, disconnect, malformed/missing receipt, or response payload that cannot be validated is not treated as rejection or success. Native keeps the prompt and in-flight response tuple, marks it unknown, disables repeat actions, and exposes an accessible warning. On disconnect, in-flight prompt responses remain unknown instead of returning to an idle/retryable state. A later `request.cancel` clears the exact server-request card. Other mutating Gateway commands still need the same typed outcome policy.

## Gateway prompt ownership

Gateway-originated approval and clarification prompts carry the connection ID and profile that delivered them. Native names prompt-state entries by that owner plus the upstream prompt/request ID, stamps connection ownership onto Gateway request and result events, and checks the owner again when rendering, responding, applying results, and processing `request.cancel`. This permits identical IDs on separate Gateway connections while ensuring an inactive connection's prompt cannot be submitted through the active connection. The scope currently covers approval, single-question clarification, batch clarification, and their cancellation/result paths; unrelated mutating Gateway operations still require an end-to-end owner audit. Server-request answer receipts now also carry the exact request profile from the response command and are applied only when both the Gateway connection and profile match the prompt; tagged receipts with a missing profile fail closed.

## Profile security and secret redaction

Native Settings now exposes the pinned security.redact_secrets preference for the selected Hermes profile. Reads and writes use profile-scoped /api/config through the authenticated remote client or verified loopback ticket. A missing setting defaults to enabled, matching Hermes. The client preserves an explicit profile opt-out and does not apply a second unconditional sanitizer to log lines; Hermes remains authoritative for secret detection and log formatting. The Command Center log view consumes the profile-scoped /api/logs response. Native headless tests cover the default, opt-out parsing, profile-scoped remote read/write, and Security tab navigation. Live Gateway and packaged Windows acceptance remain open.

PAR-0526 extends the structured transcript error card using pinned `error_surface.layer` and `error_surface.code`: provider policy/safety refusals, rejected credentials, provider timeouts, unreachable custom endpoints, and dropped response streams receive separate plain-language explanations while raw details stay collapsed. Live authenticated errors and packaged Windows interaction remain unverified.

## New-chat model policy

The New Chat composer reads `/api/model/options` for the selected single profile and Gateway connection. It presents the profile's current model as the default and treats a user-picked model/provider as a manual session override. Model options and manual selections are connection/profile scoped; a stale or differently owned selection is omitted from `session.create`. Reasoning effort follows the same ownership and is sent as the pinned `reasoning_effort` create field. Choosing “Use Hermes default” removes the manual model/provider override. These chat-local choices do not write profile configuration. Headless egui and create-flow tests cover selection, payload, profile isolation, and default preservation; profile-global main model settings and live/package acceptance remain open.

### Profile main-model settings

Settings → Main model reads the selected profile's `/api/model/options` catalog and sends `POST /api/model/set?profile=...` with `scope=main`. The Gateway's `confirm_required` receipt is shown as an explicit confirmation step; the client resubmits with `confirm_expensive_model=true` only after the user confirms. A success receipt updates only the local profile catalog snapshot. Denials and stale request/profile/connection results cannot change that snapshot. New-chat model/reasoning overrides remain separate and continue to apply only to the created session. Headless rendered tests and a token-authenticated HTTP fixture cover confirm, accept, deny and stale-connection paths; live Gateway and packaged acceptance remain open.

### Approval choice command boundary

The approval card derives actions from the choice list supplied by Hermes. Headless interaction coverage verifies that unsupported actions emit no Gateway command and supported actions carry the exact server request ID, profile, and choice. The request actor returns the server response on the same socket; receipt generation checks prevent stale acknowledgements from clearing current approval state. Live Gateway and packaged Windows interaction remain unverified.
