# Agent-operated UI and background evidence

## User requirement

A coding agent should be able to do everything a person can do through Hermes UI, and more through debugging and inspection, without repeatedly taking over the operator’s desktop.

## Current semantic runner

`cargo run --features agent-automation --bin hermes-automation -- --inspect --click Files --screenshot artifacts/agent-ui/native-shell.png` runs a headless egui_kittest/AccessKit harness over the shared `HermesNativeApp::draw` function. It can inspect the semantic tree, click or scroll over a control by accessible locator, type at the current selection or fill an accessible text field exactly, and render a screenshot at `--viewport WIDTHxHEIGHT`. It creates no native window, does not activate the desktop, does not start the Hermes gateway, and uses an isolated temporary layout profile. The runner and egui_kittest dependency require the opt-in `agent-automation` Cargo feature and are not in the default build.

This is a local development executable, not an external service. It has no authenticated Debug Bridge, complete typed capability/action registry, build supervisor, or physical Windows host control. The typed registry covers navigation, pane toggles, interface mode, layout profiles, Capabilities tabs/refresh, Toolsets enable/disable, stopping the active generation, answering visible approval/clarify prompts, and closing the active tab through `close_active_tab`; human controls call the same app-core handlers. Toolsets and session Pin/Unpin/read-state/archive writes use the bounded async gateway HTTP worker and return correlated success/error events; session mutations use the Desktop mutation snapshot fence and carry the owning profile. Archive/Unarchive is available in the cross-profile archived-session view, which the agent can open through `sessions.show-archived`; it can return to active sessions through `sessions.show-active`. Foreign-profile rows are inspectable and restorable but cannot be opened until chat operations support explicit profile scope. Stop uses the active runtime session ID and `session.interrupt`. Approval decisions are limited to the choices offered by Hermes. Single-question clarify answers use source-provided choices and generation-scoped prompt identity; skip sends the contract's empty answer. Batch server-request clarify answers are staged per question and use sequential `clarify.lock` calls; replayed answers remain editable and Skip closes the request. These prompt actions reject stale IDs and disconnected state. The accessibility tree exposes stable IDs for fixed controls and dynamic session rows/actions (`session.row.<profile>.<stored-id>`, `session.actions.<profile>.<stored-id>`, `session.pin.<profile>.<stored-id>`, `session.unread.<profile>.<stored-id>`, `session.archive.<profile>.<stored-id>`, `sessions.show-archived`, `sessions.show-active`); contributed/user controls still need IDs. It validates the shared UI drawing and egui input path; it does not prove Windows window, focus, DPI, or source parity.

The `--recent-session-reorder-fixture` option populates two recency date groups and an independent transcript pane. Recent rows expose `Reorder recent session {session_id}` drag handles only in the unfiltered active single-profile list. The fixture is synthetic and offline; its screenshot at `artifacts/agent-ui/recent-session-groups-20261115-v3.png` (with JSON provenance) shows the two groups and transcript together. Source-paired Windows visual/physical acceptance remains open.

## Opt-in child-process protocol

`cargo run --features agent-automation --bin hermes-automation -- --stdio` starts a versioned newline-delimited JSON interface over inherited stdin/stdout. It exposes health, capabilities, state, AccessKit tree, events, a diagnostics bundle, exact role/name click/type/select, keyboard input, wait-for-visible-control, screenshot capture, and close. `ui.tree` includes visible/enabled state, positive-area bounds, stable test IDs and explicit parent IDs alongside its nested accessible tree. UI actions require an expected state generation and return a structured before/after receipt. Requests are bounded and idempotent: matching retries replay a response, conflicting IDs fail, and old IDs whose response left the cache are rejected without re-executing. The process uses an isolated temporary profile, no network listener, native window, desktop focus, or Hermes gateway. Screenshot writes are restricted to new `.png` basenames under `artifacts/agent-ui`; each image is published with a same-stem `.json` sidecar containing source pins, target revision/dirty state, executable and image hashes, route, state generation, viewport scale, timestamp, fixture/profile identity and prior action receipts. Headless physical DPI is explicitly null.

The exact wire contract, bounds and error cases are in `AGENT_AUTOMATION_PROTOCOL.md`. This inherited-pipe interface is a child-process capability for a trusted parent; it is not the supplemental authenticated loopback Debug Bridge or a production service.

## Node-compatible Playwright-shaped client

`agent/hermes-page.mjs` provides a small JavaScript client over the Rust stdio protocol. Its API includes `page.getByRole(role, { name })`, `page.getByTestId(id)`, locator `click`, `fill`, `type`, `selectOption`, `scroll`, `dragTo`, `waitFor`, visibility/enabled/bounds queries, `page.press`, diagnostics/state/tree reads, and hash-bound screenshots. It launches one isolated runner by default, sequences UI mutations against the last observed generation, surfaces stale-state errors, and never retries a timed-out mutation whose outcome is unknown.

Run its client tests with `node --test apps/hermes-native/agent/hermes-page.test.mjs`. The module uses Node built-in APIs and is intended to be usable from Bun as well; this checkout has Node v24 installed and no Bun executable, so the current automated client validation runs under Node. The client controls the existing headless semantic runner, not the native OS window.

## Native background process channel (partial)

Build `hermes-automation` with `--features agent-automation`, then start `hermes-automation.exe --native-window --stdio` with inherited pipes. The process uses its own temporary profile, disables the Hermes gateway, runs off-screen with `WS_EX_NOACTIVATE`, and uses inherited stdin/stdout only. `state.get` reports route, generation and a bounded layout/profile/panel/gateway/session diagnostic snapshot; `diagnostics.bundle` adds process/window identity. `ui.tree` asynchronously reads the real window's Windows UI Automation control view, returning at most 256 nodes and depth 16 with roles, accessible names, automation IDs, action capabilities, state flags, bounds and hierarchy; it omits editable values and is bounded to eight seconds. `ui.action` accepts one exact automation ID or role/name locator from a current complete tree, then dispatches `click`, `focus`, `set_value`, or `replace_selected_text` through egui/AccessKit. Receipts verify widget response, app focus state, or a value-change event and never return entered text. Re-query the tree after each mutation. Stale, ambiguous, disabled, unsupported and malformed actions fail closed. `app.actions.list` and `app.action.execute` expose the typed app-action catalog and shared handlers; `screenshot.capture` returns a validated renderer PNG encoded as base64 with SHA-256 and viewport scale; `protocol.close` acknowledges and closes the window.

Verified native evidence: `artifacts/agent-ui/hermes-native-window-capabilities-20261115.png` and `.json` record a route transition from `/` to `/capabilities`, 2160×1350 pixels at 1.5 points scale, a 387,520-byte PNG with SHA-256 `d82f8e85934d71a72bb1cfda3771f536d7e789350bd03851fb44a311ec477ed8`, and unchanged foreground PID 5220. The profile is isolated and offline, so the screenshot only verifies that distinct native state reached the renderer. It does not compare with the pinned Hermes source.

The native interaction channel was exercised in the actual off-screen process: it found 26 controls on `/`, focused and edited `Search sessions` using `set_value` and `replace_selected_text`, clicked `Capabilities`, and observed `/capabilities` with 30 controls. A real `HermesPage.launchNative()` session resolved the `Capabilities` locator, navigated to `/capabilities`, dispatched Ctrl+P and Escape with state readback, and captured a 2160×1350 PNG. It also selected Simple/Advanced interface modes and Basic/Default layout profiles through visible ComboBox options, confirming each from native app state. The keypress receipts remained fail-closed until state verification. The process closed cleanly, and prior foreground-owner monitoring never observed the Hermes process in front. UIA's native `focused` flag did not mirror egui focus, so focus success is established by the app-side response and the subsequent confirmed text action. Coordinate `ui.click` remains explicitly unverified. The new generation-fenced `ui.wheel`/`HermesPage.wheelAt()` path was visually verified on the live 2,379-entry Plugins catalog: the screenshot digest changed and different plugin cards occupied the viewport. Exact-target `ui.scroll` still requires a complete UIA tree, which timed out on this dense view; native drag/drop remains open. This is isolated target behavior, not live gateway use or pinned-source acceptance.

try {

## Intended external interface

Expose stable semantic locators backed by native accessibility information and explicit test IDs. A client should be able to inspect the visible control tree and query by role, accessible name, test ID, enabled/visible state, and bounds. Provide Playwright-like actions: click, fill/type, select, modified keypress including tab cycling, bounded pointer drag, wait for a condition, and capture a screenshot. Each action must enter the same application event/handler path used by a human.

The runtime should return structured action receipts with target identity, before/after state, and errors. Locators should be stable across visual restyling and scoped to the running app instance. The native Accessibility tree remains available to ordinary Windows UI Automation clients and screen readers. Coordinate input is a fallback and physical-host verification method, not the primary control architecture.

## More than a person can do

Add a separate local authenticated Debug Bridge for capabilities, bounded state/layout/panels/windows, logs, events, diagnostics, action preview/execute and reload status. Diagnostic commands may inspect richer state; mutations must still follow app permissions, Hermes approvals, destructive confirmations and canonical DoofusDock transactions. The bridge is distinct from Hermes gateway and disabled/absent in production.

## Unattended operation

Run isolated Hermes Native instances with dedicated app data and an isolated Hermes profile or deterministic fixture backend. Do not take foreground focus, send input to the operator’s active window, or write to the installed Hermes profile. Use an isolated live profile for protocol acceptance; do not reuse a user session for mutating scenarios. The headless runner is the current non-disruptive path.

Store screenshots and traces as reviewable evidence with timestamp, source SHA, executable build ID, process generation, route, viewport/DPI, fixture/profile identity, state/layout revision, and action receipts. Keep headless, semantic integration, and physical Windows evidence separate.

## Acceptance

- Agent can discover controls by semantic locator rather than screen coordinates alone.
- Agent can navigate, scroll, type, fill, select, right-click context menus, open/close panels and dialogs, and invoke keyboard paths through the same handlers as human input.
- State changes and failures are observable and have structured receipts.
- Screenshots and interaction traces can be captured from a non-foreground isolated instance without disrupting the operator.
- Diagnostics expose additional state but cannot silently execute a user-facing mutation or bypass a confirmation.
- The same interaction succeeds through human input and the automation interface; parity claims require both evidence paths.
